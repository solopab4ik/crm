# Orbit / Mini CRM

## Стек

React 19, TypeScript, Next.js (App Router), Netlify Functions, PostgreSQL через Netlify Database, SQL-миграции, Lucide для иконок. Интерфейс на русском языке, адаптирован для телефона и компьютера.

## Тестовые аккаунты

| Роль | Email | Пароль |
|---|---|---|
| Client | client@mini-crm.test | CrmDemo!2026 |
| Employee | employee@mini-crm.test | CrmDemo!2026 |
| Admin | admin@mini-crm.test | CrmDemo!2026 |

Это демонстрационная система: тестовые аккаунты и примеры клиентов создаются один раз в базе при первом запросе. Сайт публикуется на Netlify; указанные демонстрационные аккаунты работают внутри приложения. Для эксплуатации с реальными клиентами необходимо убрать демонстрационное заполнение и публичную подсказку с паролями, организовать персональный выпуск учётных записей и настроить аудиторию сайта.

## Архитектура

`app/page.tsx` — рабочий интерфейс, вход, регистрация, панели, таблицы, карточки, Kanban. `app/globals.css` — адаптивное оформление. `app/api/[[...path]]/route.ts` — серверные API и авторизация. `lib/crm.ts` — доступ к PostgreSQL, хэширование, начальное заполнение, журнал. `lib/database.ts` — параметризованные запросы и транзакции. `netlify/database/migrations/` — SQL-миграции PostgreSQL. Старые `db/schema.ts` и `drizzle/` описывают прежнюю D1 и не используются при деплое. `scripts/test-api.mjs` — интеграционные проверки прав доступа.

Браузер обращается к API своего origin. Сервер извлекает токен из HttpOnly cookie, хэширует его и ищет действующую сессию в PostgreSQL. Роль и статус блокировки каждый раз берутся из базы, а не из запроса. Затем проверяются права на действие и принадлежность объекта. Только после этого выполняются SQL-запросы с параметрами. Авторитетные данные хранятся в базе, а не в localStorage.

Таблицы: users, clients, notes, sessions, logs, settings, attempts. Связь clients.user_id уникальна: аккаунту принадлежит максимум один профиль. При удалении аккаунта профиль остаётся, его user_id становится NULL. При удалении клиента удаляются его заметки; при удалении аккаунта удаляются сессии. Схему создают миграции, runtime добавляет только демонстрационные данные.

## Роли и права

| Действие | Client | Employee | Admin |
|---|---|---|---|
| Профиль клиента | Только собственный | Все | Все |
| Список, поиск, фильтры, сортировка | Нет | Да | Да |
| Создание клиентов | Нет | Да | Да |
| Редактирование контактов | Свои имя, email, телефон | Все | Все |
| Компания, статус, приоритет | Нет | Да | Да |
| Удаление клиентов | Нет | Нет | Да |
| Заметки | Только разрешённые собственные | Читать и добавлять | Читать и добавлять |
| Kanban | Нет | Да | Да |
| Пользователи, роли, блокировки | Нет | Нет | Да |
| Настройки и полный журнал | Нет | Нет | Да |

Удаление клиентов ограничено Admin, потому что вместе с клиентом удаляется история заметок. Сотрудник может выполнять повседневную работу без права уничтожить запись. Администратор не может удалить или заблокировать самого себя либо изменить свою роль; это сохраняет доступ к управлению.

Регистрация всегда назначает Client, даже если передать role=Admin. При переводе пользователя в Client сервер создаёт профиль, если его нет. При изменении роли или блокировке все сессии пользователя отзываются. Email профиля является контактным и не меняет логин учётной записи.

Client Dashboard показывает профиль, статус и общедоступные сообщения с датами. Employee Dashboard показывает количество клиентов по статусам, воронку, последние записи и изменения. Admin дополнительно видит число пользователей по ролям и активных аккаунтов, управление сотрудниками и полный журнал действий. Под активным аккаунтом понимается незаблокированный аккаунт, а не онлайн-пользователь.

## Безопасность

Пароли хэшируются PBKDF2-SHA256 с индивидуальной случайной солью и 100 000 итераций (Web Crypto); сравнение проходит полный хэш без раннего выхода. Токены сессий случайные, в базе хранится SHA-256 токена; срок — 24 часа. Cookie: HttpOnly, SameSite=Strict, Secure при HTTPS. Logout отзывает серверную сессию.

Все мутации требуют Origin, совпадающий с origin приложения. Используются параметризованные SQL-запросы, лимиты длины полей и JSON, экранирование React и ограничение попыток входа/регистрации по IP и email (10 за 15 минут). API не возвращает хэши паролей. Client не может читать чужой профиль или заметки изменением ID. Изменение роли в отправленном JSON не изменяет права сессии.

Это небольшая демонстрационная CRM. В ней нет восстановления пароля, подтверждения email, MFA, отправки email и распределённого мониторинга; они не входили в обязательные пользовательские сценарии. Аудит сохраняет имя исполнителя, действие, объект и UTC дату/время; интерфейс отображает время Asia/Qyzylorda. Текстовые имена в журнале сохраняются после удаления аккаунта.

## Дополнительные функции

Kanban-доска с четырьмя колонками: Новый, В работе, Успешный, Потерян. Перетаскивание карточки отправляет PATCH на сервер, который повторно проверяет роль. На телефоне и с клавиатуры статус можно менять через select в карточке. Фильтры и поиск работают и на доске. Высокий приоритет помогает выделять важные контакты.

## Запуск и проверки

Node.js 22. `npm ci`, `npm run build`. Для локального запуска с базой: `npx netlify link`, затем `npx netlify dev`.

`npm run test:postgres` запускает 40 проверок API и безопасности на временной PostgreSQL (PGlite), а также проверяет миграцию, откат транзакций, поиск без учёта регистра и внешние ключи. Рабочая база при этой проверке не используется. `node scripts/test-api.mjs` можно запускать отдельно на тестовом сервере; этот вариант изменяет данные.

Публикация: `npx netlify deploy --prod --context production`. Конфигурация: `netlify.toml`, build `npm run build`, publish `.next`, base directory пустой. Netlify автоматически создаёт PostgreSQL и применяет миграции из `netlify/database/migrations/`. Новую миграцию создавайте через `npx netlify database migrations new`; уже применённые миграции не редактируются. Секреты базы хранятся на платформе. Старая локальная D1 остаётся отдельной базой; данные автоматически не копируются.

## Как объяснить проект

1. Скрытие пунктов меню улучшает интерфейс, но доступ защищает серверная проверка каждой операции.
2. Проверка роли Client недостаточна: сервер дополнительно сравнивает clients.user_id с users.id.
3. Заметки разделены флагом visible, который фильтруется SQL-запросом для клиента.
4. Сервер игнорирует роль при регистрации, поэтому подмена JSON не повышает привилегии.
5. Роль читается из users на каждом запросе, а сессии отзываются при изменении доступа.
6. PostgreSQL сохраняет данные независимо от браузера, а миграции позволяют воспроизвести структуру базы.
